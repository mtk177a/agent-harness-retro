# 報告の要件

報告は依頼に合わせて構成し、直接の観測、所見、原因仮説、提案する解決策を区別する。

## 判断の記録

- **範囲:** 対象、証拠の範囲、重要な網羅性の制約を示す。
- **所見:** 裏付けられたパターンと影響を説明し、原因仮説とその不確実性を観測から分け、所見に解決策を含めない。
- **証拠:** 安定した参照を使い、観測、所見、判断を、`source_ref`、検証済みの版、範囲を限定したイベント、関連する確認済みの現在のハーネスの構成要素とその版に結び付ける。
- **判断:** 結果、選んだ責任範囲と対応の仕組み、選択や却下の理由、判断を変え得る未解決情報を示す。

各提案に、次を含める。

- **変更:** 対象リポジトリかグローバルな構成要素、範囲、意図する最小限の編集。
- **理由:** 根拠となる所見と証拠、期待する改善、重要なトレードオフ。
- **引き継ぎ:** 検証方法、承認者、実装担当を示し、人名が示されていなければ役割名を使い、グローバルな提案では対象の構成要素の所有者を示す。

## 対応の仕組み

| コード | 使用する場合 |
| --- | --- |
| `memory_candidate` | 一時的かユーザー固有の知識を引き継ぐ場合。この分類は、メモリへの書き込みや独自の保存先の作成を許可しない。 |
| `global_instructions` | 実質的に異なる複数のリポジトリの文脈で、安定した行動原則が裏付けられる場合。 |
| `repository_guidance` | 1 つのリポジトリに固有の、永続的なエージェント向け知識の場合。 |
| `repeatable_skill` | 条件付きで再利用できる判断や複数手順のワークフローが不足している、または誤って振り分けられている場合。 |
| `hook_ci_rule` | 条件を決定論的に強制でき、そうすべき場合。 |
| `canonical_project_change` | 正しさや知識が、プロジェクトの実装、テスト、正式な文書に属する場合。 |
| `one_off_action` | 局所的で一時的な対応で、永続的な仕組みを必要としない場合。 |
| `no_persistent_change` | 既存の制御で十分な場合、プロバイダーが管理する挙動である場合、永続的な変更を正当化できない場合。 |
