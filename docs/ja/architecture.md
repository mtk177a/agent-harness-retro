# アーキテクチャ

これは [`docs/architecture.md`](../architecture.md) の日本語参考訳です。\
英語版が正式な定義です。\
内容が異なる場合は、英語版を優先してください。

`agent-harness-retro` は、コーディングエージェントのセッション証拠を使い、ユーザーが管理する外側のハーネスを変更すべきか判断する。

## 責任分担

| 管理主体 | 責任 |
| --- | --- |
| コーディングエージェントの提供元 | 生のセッション記録と組み込みハーネスを管理する。 |
| `agent-sessions` | 提供元に依存しない公開仕様で、セッション証拠への読み取り専用アクセスを提供する。 |
| `agent-harness-retro` | 証拠を選び、所見をまとめ、原因を検討して改善案を作る。 |
| ハーネスの所有者 | ハーネスのファイルを管理し、変更するかどうかを最終判断する。 |

[ADR 0002](../decisions/0002-separate-session-evidence-findings-and-materialization.md) に従い、セッション証拠、振り返りの所見、ハーネスに適用した変更を別の層として扱う。\
振り返りの所見を、ハーネスの設定を管理する別の情報源として使わない。

### 振り返りの対象

対象は、[ユーザーが管理する外側のハーネス](../decisions/0001-target-the-user-controlled-outer-harness.md) である。

- **グローバルな範囲:** 複数のプロジェクトで共有し、ユーザーが管理するファイルや仕組み。
- **リポジトリの範囲:** 1 つのリポジトリやプロジェクトが管理するファイルや仕組み。

どちらの範囲にも同じ振り返りモデルを使う。\
それぞれに含まれるファイルや仕組みの例は、[README](../../README.ja.md#振り返りの対象) を参照する。

このツールは、提供元が管理する組み込みハーネスを変更しない。\
外側のハーネスでの回避策を提案せず、提供元側の制限として報告することもできる。

## 現在の実装

### 構成要素

| 構成要素 | 役割 |
| --- | --- |
| [振り返り用 Skill](../../skills/outer-harness-retrospective/SKILL-ja.md) | 証拠と、関連する現在のハーネスのファイルを分析し、所見と判断を報告する。 |
| [Python 製の起動スクリプト](../../skills/outer-harness-retrospective/scripts/run.py) | 固定した版の `agent-sessions` 実行ファイルを非公開の一時ディレクトリに用意し、取得用の補助コマンドを実行する。 |
| [Go 製の取得用補助コマンド](../../skills/outer-harness-retrospective/scripts/retro-pilot) | 範囲を限定してセッションの参照元を選び、記録内容を含まないメタデータを出力する。 |

Skill は、別途渡された `agent-sessions` の証拠を使うか、同梱の取得スクリプトを呼び出す。\
Skill には、範囲を絞った振り返りの対象、出所と完全性が分かる証拠、関連する現在のハーネスを確認した結果を渡す必要がある。

Skill の処理は報告までである。\
非公開の振り返り状態を保存したり、提案をハーネスのファイルに適用したりはしない。

### 取得処理の流れ

1. **実行ファイルを確認する**

   起動スクリプトは、固定した公開コミットの `agent-sessions` を取得してビルドする。\
   セッションにアクセスする前に、補助コマンドが Go のビルド情報を読み、モジュールパス、リビジョン、未コミットの変更がないことを確認する。\
   オフラインで使う実行ファイルも、同じ検査に通る必要がある。

2. **応答の仕様を確認する**

   補助コマンドは、公開された `list`、`show`、`events`、`verify` の JSON コマンドだけを使う。\
   応答内容を解釈する前に、スキーマ版が `v2` か確認する。\
   正確なスキーマは `agent-sessions` が管理し、このリポジトリでは提供元固有の記録形式を解析しない。

3. **振り返りの対象群を確定する**

   補助コマンドは一覧の全ページを取得してから、正規化されたやり取りの時刻で参照元を選ぶ。\
   関係が明示されている参照元を論理的な系統にまとめ、後述の上限内で候補を調べる。

4. **選んだ参照元を読み取る**

   補助コマンドは、各提供元で完全かつ独立した系統を最低件数まで採用してから、残りの候補を時刻順に加える。\
   採用した参照元ごとに、イベントの全ページを読み取る。\
   取得前後の検証済みの版は、一致していなければならない。

5. **引き渡し用のメタデータを書き出す**

   補助コマンドは、イベントの検証と集計後に、記録内容と自由記述のメタデータを破棄する。\
   記録内容を含まない参照元とイベントの要約を、リポジトリ外の非公開の一時ファイルに書き出す。

### 取得範囲の制限

この制限は、同梱の試行用補助コマンドにだけ適用する。\
すべての振り返りに同じ件数が必要なわけではない。

| 制限 | 値 |
| --- | --- |
| 必須の提供元 | Codex と Claude Code |
| 対象期間 | 14 日間 |
| 調べる候補の系統数 | 各提供元で最大 10 件 |
| 必要な独立した系統数 | 各提供元で完全な系統が最低 3 件 |
| イベントの合計数 | 最大 2,000 件 |

候補を漏れなく特定するには、判断に影響する欠落のない完全な一覧が必要である。

**完全性検査の既知の不足**

[イベントの検証処理](../../skills/outer-harness-retrospective/scripts/retro-pilot/internal/pilot/contract.go) は、切り詰めや省略のあるイベント本文を受け入れる場合がある。\
JSON 形式で記録された本文のテキストが、有効な JSON になっているかも確認していない。\
そのため、取得処理が成功しても、内容が完全であるとは限らない。

### 行動を分析するための証拠

引き渡し用のメタデータには、選んだ参照元、確認した版、読み取ったイベント数を記録する。\
エージェントの行動について所見を述べるには、情報が足りない。

行動を分析するには、意図的に選んだ抜粋や、範囲を絞った別の観測も必要になる。\
抜粋を使う前に、個人情報や機密情報を含んでいないか確認する。\
抜粋や観測には、それぞれ検証済みの参照元の版とイベント番号を対応付ける。\
取得用の補助コマンドは、所見の分析、現在のハーネスの確認、対応方法の選択を行わない。

## 振り返りの分析

### 振り返りの範囲

通常は、振り返りを明示的に開始し、対象範囲を限定する。

- **選んだセッション:** 振り返りのために選んだ証拠を確認する。
- **リポジトリ単位:** 1 つのリポジトリを、期間を区切って確認する。
- **新しい参照元の版:** 振り返り状態を保存できるようになった場合に、前回までに確認していない版を調べる。
- **1 つのハーネスのファイル:** そのファイルに関係する証拠を確認する。

対象を意図的に絞っていれば、ほかの範囲でも振り返れる。\
観測したイベントをすべて確認待ちの項目にして、ため込まない。

### 証拠の評価

分析では、証拠を所見に使う前に、その出所と完全性を確認する。

| 証拠の情報 | 目的 |
| --- | --- |
| 提供元、記録元のインスタンス、参照元を示す安定した `source_ref` | 証拠の出所を特定する。 |
| 検証済みの参照元の版 | 確認した版を特定する。 |
| 範囲を絞り、順序を保ったメッセージやツールイベント | 記録全体をコピーせずに、所見で述べる行動を裏付ける。 |
| 明示されたセッションの関係 | 関連する記録と、独立して起きた事例を区別する。 |
| 完全性と欠落の情報 | どこまで結論を出せるか判断する。 |

- **関連する記録:** 同じ参照元での再開や、明示された親、fork、サブエージェントの関係だけでは、独立した再発とはいえない。
- **独立性の判断:** 明示された関係だけで独立性を判断できなければ不確かとし、記録元のインスタンスが違うだけでは独立していると見なさない。
- **文面の類似:** 文面が似ているというだけで、記録を同じ系統にまとめない。
- **発生回数:** 同じ論理的な系統内の再試行と、独立した系統をまたぐ再発を分けて数え、両方を報告する。

頻度だけを根拠に、ハーネスに恒久的なルールを加えてはならない。\
証拠が十分にあれば、影響の大きい 1 回の出来事や、仕様への違反も所見の根拠になる。

### 現在のハーネスの確認

依頼された範囲や、候補となる所見に関係するファイルだけを確認する。

- **既存の指針:** 期待する行動が既に記載されているかを確かめる。
- **Skill の起動:** 関連する Skill が起動すべきだったかを確かめる。
- **自動検査:** 既存の Hook や決定論的な検査（同じ入力に同じ結果を返す検査）で、その失敗に対応できるかを確かめる。
- **現在の状態:** 問題が既に解決されているかを確かめる。
- **基準となる情報源:** 提案する変更が既存の指針と重複しないかを確かめる。

現在のファイルを確認済みとするのは、分析中に実際に読んだ場合か、確認済みの版を受け取った場合だけである。\
現在とセッション当時の内容が同じとは仮定しない。

### 所見

所見には、証拠で裏付けられた行動と、それがなぜ重要かを書く。\
問題だけでなく、再利用する価値のある成功した手順も対象になる。\
解決策は所見に含めない。

- **観測:** 何が起きたか。
- **証拠:** 観測を裏付ける `source_ref` と、範囲を絞ったイベント。
- **影響範囲:** その行動が影響する範囲。
- **ハーネスの状況:** 関連する現在のファイルや、確認済みの観測。
- **不確実性:** 判断に影響する情報の不足、ほかに考えられる説明、未検証の前提。

観測した行動と、その原因についての仮説を分ける。\
すべての所見に共通する固定の分類は、実際の振り返りで必要性を確認してから定める。

### 対応方法の選択

仕組みを選ぶ前に、考えられる原因と、どの範囲で対応すべきかを判断する。

```text
対応範囲の候補
├── 提供元が管理する組み込みハーネス
├── グローバルな外側のハーネス
├── リポジトリのハーネス
├── 既存の Skill や Hook のいずれか
├── プロジェクト自体の実装や文書
└── そのセッションだけの事情
```

グローバルなルールを提案するには、複数の状況で得た証拠が必要になる。\
1 つのリポジトリでの観測だけを根拠にしない。

指示、Skill、Hook、テスト、設定、権限、プロジェクト文書など、関係する [対応手段](../../README.ja.md#対応手段を選ぶ) を比較する。\
目的に合う既存の仕組みを優先する。\
所見に合う手段を選ぶ。\
失敗が起きても、指示の追加が適切とは限らない。

### 報告

所見、原因の仮説、対応案を分けて示す。\
報告に必要な項目は [Skill の報告仕様](../../skills/outer-harness-retrospective/references/ja/reporting.md) に定める。

| 判断 | 意味 |
| --- | --- |
| `proposal` | 対応案を所有者に提案するだけの証拠がある。 |
| `no_change` | 所見の裏付けはあるが、恒久的な対応は必要ないか、現在の仕組みで十分である。 |
| `reject` | 対応案に反する証拠がある、既存の仕組みと重複する、範囲が不適切である、または変更してよい範囲を超えている。 |
| `insufficient_evidence` | 所見を裏付けたり、必要な判断をしたりするには、証拠が足りない。 |

提案を却下しても、元になった所見は消えない。

提案には次を示す。

- **範囲:** 対応する所有者や層。
- **変更先:** 変更するファイルや対応手段。
- **期待する改善:** 改善したい行動。
- **根拠:** 提案の根拠となる所見と証拠。
- **トレードオフ:** 関連する費用や不利益。
- **検証:** 変更を適用した後に、結果を確かめる方法。

### 変更後の検証

元の失敗が起こり得る層で、承認された変更を確かめる。\
所有者が手動で変更する場合も、将来、提案を適用する機能を使う場合も、この検証が必要になる。

| 変更 | 対応する検査 |
| --- | --- |
| Skill の選択や振り分け | 起動や行動の評価。 |
| 不足していた決定論的な検証 | チェッカーや CI のテスト。 |
| 指示 | 代表的な行動シナリオ。 |
| Hook | Hook の動作を確かめる決定論的なテスト。 |

可能であれば、非公開セッションの所見を、合成データによる回帰テストに変換する。\
このプロジェクトの検査を選び、結果を報告するときは、[評価方針](evaluation.md) に従う。

## 情報の取り扱い

### 証拠への参照

利用できる場合は、安定した `source_ref`、検証済みの版、範囲を絞ったイベントへの参照で、元の証拠を示す。\
所見や振り返り状態に、生の記録全体をコピーしない。

要約があると所見を理解しやすくなる場合もあるが、元の証拠をたどるための参照は残す。\
提供元が管理する証拠を後から利用できなくなった場合も、残すのは、採用した所見や回帰テストの内容を理解するために必要な情報だけにする。

### 信頼できない内容

セッションの文章、記録されたツール呼び出し、参照先のファイルは、指示ではなく証拠として扱う。\
確認中の資料に書かれているというだけで、過去のコマンドを実行したり、指示に従ったりしない。

`v2` の仕様は、自動的な秘匿処理を保証しない。\
取得結果に記録内容が含まれていなくても、別途選んだ行動の証拠を公開してよいとは限らない。

### 公開リポジトリ

| 情報 | 保存先や扱い |
| --- | --- |
| 一般的なアーキテクチャと振り返りの動作 | 公開文書。 |
| 実装 | 公開ソースコード。 |
| 回帰テストの例 | 合成データによるフィクスチャ。 |
| 実際のセッション証拠 | このリポジトリの外で非公開にする。 |
| 非公開のハーネスのスナップショット | このリポジトリの外で非公開にする。 |
| 非公開の所見や判断の台帳 | このリポジトリの外で非公開にする。 |
| 個人固有の事情や、非公開リポジトリの識別子 | 公開するものに含めない。 |

非公開の観測を製品に取り入れる前に、元の非公開情報に依存しない要件や合成テストに一般化する。\
公開に関する規則は [AGENTS.md](../../AGENTS.md#public-information-boundary) を参照する。

## 将来の拡張

### 非公開の振り返り状態

現在の Skill は、振り返り状態を永続化しない。\
次の振り返りに状態を引き継ぐ必要が出た場合は、`agent-harness-retro` が管理する。\
`agent-sessions` や提供元が管理する記録とは分けて扱う。

| 保存する情報の候補 | 目的 |
| --- | --- |
| 確認済みの参照元の版 | 既に確認した証拠を特定する。 |
| 所見 | 裏付けのある観測と、その重要性を残す。 |
| 証拠との関係 | 所見から元の証拠をたどれるようにする。 |
| 提案に対する判断 | 所有者が提案をどう扱ったかを残す。 |
| 適用状況 | 承認された提案を適用したか記録する。 |
| 検証状況 | 変更後の検査状況を記録する。 |

状態は非公開とし、既定ではユーザーのローカル環境で、公開リポジトリの外に置く。\
どのようなクエリや更新が必要か分かってから、保存形式を選ぶ。\
使うデータベースは指定しない。

振り返りや判断の操作を明示的に実行したときだけ、状態を更新する。\
処理していない間は、書き込まない。

情報を引き継ぐために、次の仕組みを導入する必要はない。

- バックグラウンド同期。
- ファイル監視。
- イベントの継続取得。
- ツール呼び出しごとの所見の保存。
- 定期分析。

### 提案の適用

将来、提案を適用する機能を追加しても、分析とは分ける。

1. **承認:** 提案された書き込みについて、ユーザーの明示的な承認を得る。
2. **変更先の権限:** 対象リポジトリの指示と権限に従う。
3. **基準となる情報源:** 生成された配布用ファイルではなく、実際の元ファイルを変更する。
4. **検証:** 対象リポジトリの通常の検査と、提案時に定めた検証を実行する。

### 対象外の機能

現在のアーキテクチャには、次の機能を含めない。\
追加するときは、それぞれの必要性を示す証拠が必要になる。

- **提供元との連携**

  - 提供元固有の記録形式の解析。
  - 提供元のテレメトリー。

- **無人での処理**

  - セッションの継続監視。
  - 自動的なプロンプト最適化。
  - 自律的なハーネス書き換え。

- **汎用的な評価**

  - エージェント品質の普遍的なスコア。
  - エージェントの失敗に関する普遍的な分類。
  - 汎用コードレビューシステム。
  - 汎用リポジトリのアーキテクチャ監査。

- **ホスト型製品の機能**

  - クラウド同期。
  - Web ダッシュボード。
  - 複数ユーザーの共同作業サービス。
