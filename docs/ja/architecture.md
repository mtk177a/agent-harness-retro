# アーキテクチャ

これは [`docs/architecture.md`](../architecture.md) の日本語参考訳です。\
英語版が正式なアーキテクチャ定義であり、差異がある場合は英語版を優先してください。

## 目的

`agent-harness-retro` は、正規化されたセッション証拠を使って、ユーザーが管理するコーディングエージェントのハーネスを振り返り評価する。

責務は次に限られる。

- 関連するセッション証拠を選ぶ。
- 繰り返し現れる、または重要な挙動を観測する。
- 挙動を現在の外側のハーネスと関連付ける。
- 所見を記録する。
- 可能性の高い対象範囲と制御面を判断する。
- 証拠に基づく改善提案を作る。
- 永続状態が必要な場合に振り返りの判断を追跡する。

プロバイダー固有のセッション取得は、この境界の外にある。

## システム境界

```text
Provider-owned sessions
        │
        ▼
   agent-sessions
        │
        │ normalized evidence
        ▼
agent-harness-retro
──────────────────────────────────

evidence selection
current harness observation
retrospective analysis
findings
scope resolution
proposal generation
decision state

        │
        ▼

User-controlled outer harness
──────────────────────────────────

global outer harness
repository harness
```

| 主体 | 所有するもの |
| --- | --- |
| コーディングエージェントのプロバイダー | 生のセッション記録と組み込みハーネス |
| `agent-sessions` | プロバイダーに依存しない、読み取り専用のセッションアクセス |
| `agent-harness-retro` | 振り返りの所見、証拠の関係、提案 |
| ハーネスの所有者 | 実際の外側のハーネスの成果物と、最終的な変更判断 |

## 対象境界

### 組み込みハーネス

言語モデルをコーディングエージェント製品として使えるようにする、ベンダー管理の仕組み。

例として、プロバイダーが所有する次のものがある。

- システムプロンプト。
- コンテキスト管理。
- 内部オーケストレーション。
- ツール実行環境。
- 製品内部のメモリ。
- 内部ルーティング。

`agent-harness-retro` は組み込みハーネスに関連して見える挙動を観測できるが、その層は変更しない。\
組み込み側の制限は、不適切な外側のハーネスの回避策に変換せず、そのような制限として報告できる。

### 外側のハーネス

組み込みのコーディングエージェントのハーネスを取り囲む、ユーザーが管理する層。\
`agent-harness-retro` の主な対象である。

### グローバルな外側のハーネス

複数のリポジトリまたはプロジェクトに影響を与えることを意図した、ユーザー管理の成果物。

含まれる可能性がある成果物は次のとおり。

- グローバル指示。
- グローバル Skill。
- ユーザー用 Hook。
- ユーザーが管理する設定と権限。
- 再利用可能なエージェント定義。
- 共有 MCP またはプラグインの設定。

### リポジトリのハーネス

1 つのリポジトリまたはプロジェクトが所有する、エージェント向けの制御面。

含まれる可能性がある成果物は次のとおり。

- リポジトリ指示。
- リポジトリ固有の Skill。
- リポジトリの Hook と設定。
- エージェント向けのプロジェクト文書。
- 同じ条件で同じ結果を返すリポジトリのコマンド。
- テストと CI。
- 評価用アセット。

同じ振り返りモデルをグローバルの対象範囲とリポジトリ固有の対象範囲に適用する。

## 入力の仕様

`agent-harness-retro` は `agent-sessions` を通じてセッション証拠を受け取る。\
プロバイダー固有の Codex、Claude Code、その他の生のトランスクリプト形式に直接依存してはならない。

実装済みの Skill は、安定した `agent-sessions` `v1` 仕様に沿って提供された証拠を受け取る。\
そこには次が含まれる。

- 安定した情報源への参照。
- プロバイダー。
- 情報源のインスタンス。
- 情報源の版。
- セッションの関係。
- 順序付けられたメッセージとツールイベント。
- 完全性と欠落の情報。

正確な上流スキーマは `agent-sessions` が管理する。

## 実装済みの提案専用 Skill

初期実装は、プロバイダーアダプターや `agent-sessions` を直接呼び出すのではなく、提供された正規化済み証拠を受け取るエージェント向け Skill である。\
必須入力は、意図的に範囲を限定した証拠集合、要求された対象範囲、関連する現在の外側のハーネスの観測である。

Skill は出所と完全性を検証し、明示的に関係付けられた情報源を論理的な系列にまとめ、系列内の再試行とセッション間の再発を区別してから、所見と提案専用の判断を作る。\
同じ情報源への参照での再開の観測と、明示された親または fork 関係は、独立した再発を作らない。\
関係が曖昧な場合は、内容が似ていることから推測せず、不確かなまま扱う。

実装された結果の境界は次のように分かれる。

```text
observation
      │
      ▼
finding
      │
      ▼
cause hypothesis
      │
      ▼
scope and routing assessment
      │
      ▼
proposal | no change | reject | insufficient evidence
```

この実装は、セッションのライブ取得、非公開の継続状態、自動的な実体化、パッケージ化とインストールの機能を提供しない。\
これらの責務には別の証拠と変更が必要である。

## 現在のハーネスの確認

振り返りはセッション証拠だけを対象に行わない。\
分析器は、次を判断できるだけの現在のハーネスの文脈も必要とする。

- 関連する指針が既に存在するか。
- Skill が起動すべきだったか。
- Hook または同じ条件で同じ結果を返す検査が既にその失敗を対象にしているか。
- 所見が既に解決されているか。
- 提案する変更が別の基準文書と重複しないか。

ハーネスの観測は対象範囲に限定する。\
存在するというだけで、すべてのグローバルとリポジトリの成果物を読み込まない。\
候補となる所見または要求された振り返りの対象範囲に関連する成果物だけを読む。

## 振り返りの流れ

概念上の処理の流れは次のとおり。

```text
select evidence
      │
      ▼
observe behavior
      │
      ▼
identify finding
      │
      ▼
check current harness
      │
      ▼
resolve likely cause and scope
      │
      ▼
compare control surfaces
      │
      ▼
produce proposal or no-change decision
```

この処理の流れは概念であり、1 つの実装手順を要求するものではない。

## 所見

所見は、セッション証拠に支えられた重要な観測を記録する。

例として次がある。

- ユーザーによる修正の繰り返し。
- 不要な再試行の繰り返し。
- 対象範囲の逸脱。
- 検証の不足。
- 効果のない指示。
- Skill の振り分けまたは起動の失敗。
- 不適切な委任。
- 繰り返し成功する手順。
- 重複または競合するハーネスの指針。

初期実装では、実際の振り返りで必要性が示される前に、広範で普遍的な分類を固定しない。

### 所見の要件

重要な所見には次を示す。

- 何を観測したか。
- 観測を支える証拠。
- 影響を受ける対象範囲。
- 関連する現在のハーネスの文脈。
- 重要な場合の不確実性または代替説明。

所見は解決策を指定しない。

## 原因と対象範囲

繰り返す挙動は異なる層から生じる可能性がある。

```text
same observed failure
        │
        ├── built-in harness limitation
        ├── global outer-harness guidance
        ├── repository harness
        ├── one Skill or Hook
        ├── project implementation
        └── one-off session context
```

振り返りでは、すべての失敗を指示の変更へ変換してはならない。\
対象範囲の解決は中核責務である。

## 制御面

提案は、所見と対象範囲を確定してから制御面を選ぶ。

| 必要なもの | 典型的な制御面 |
| --- | --- |
| 永続的な行動指針 | 指示またはルール |
| 条件付きの判断手順 | Skill |
| 機械的な介入 | Hook |
| リポジトリの不変条件 | テスト、チェッカー、または CI |
| ユーザーが管理する実行挙動 | 設定または権限 |
| プロジェクトの基準情報 | リポジトリ文書 |
| 既存の挙動で既に十分 | 変更なし |

この表は指針であり、固定的な対応表ではない。

## 提案

提案は、1 つ以上の所見への候補対応である。\
提案には次を示す。

- 対象範囲。
- 対象成果物または制御面の種類。
- 期待する効果。
- 証拠。
- 既知のトレードオフ。
- 実体化後に必要な検証または評価。

システムは変更なしの結果を扱える必要がある。\
挙動が繰り返されたことだけでは提案を正当化できない。

## 証拠モデル

所見は完全なトランスクリプトを複製せず、情報源の証拠を参照する。

可能な場合、証拠には次を使う。

- 情報源への参照。
- 検証済み情報源の版。
- 範囲を限定したイベント参照。

派生した要約は使いやすさのため保持してよいが、元の証拠の関係に代わるものではない。

プロバイダーが所有する証拠を後で利用できなくなっても、保持した証拠には、承認済みの所見または回帰を防ぐための要件を理解するために必要な最小限を残す。

## 非公開の振り返り状態

`agent-sessions` とは異なり、`agent-harness-retro` は利用者が所有する永続状態を必要とする可能性がある。

考えられる状態は次のとおり。

- 既に確認した情報源の版。
- 所見。
- 証拠の関係。
- 提案の判断。
- 実体化の状態。
- 検証の状態。

この状態は次の性質を持つ。

- 非公開である。
- 既定ではユーザーのローカルにある。
- 公開リポジトリとは分離される。
- プロバイダー所有のトランスクリプトとは分離される。
- `agent-sessions` とは分離される。

初期アーキテクチャは SQLite や特定のストレージ形式を定めない。\
必要な検索と更新のパターンが分かってから、ストレージ実装を選ぶ。

### 書き込み動作

実行時の状態は、意図的な振り返りまたは判断操作を通じてのみ更新する。\
アーキテクチャは次を要求しない。

- バックグラウンド同期。
- 継続的なイベント取り込み。
- ファイルウォッチャー。
- ツール呼び出しごとの候補の永続化。
- 定期的なセッション分析。

アイドル時の書き込みは 0 のままにする。

## 分析の頻度

既定のモデルは、明示的に行う振り返り分析である。\
振り返りの対象には次がある。

- 選択したセッション。
- リポジトリと期間。
- 前回以後の新しい情報源の版。
- 1 つのハーネス成果物に関連する証拠。
- その他の意図的に限定した対象範囲。

システムは、観測したすべてのイベントについて候補となる所見を継続的に作らない。\
これにより、通常のエージェント活動が増え続けるレビューキューに変わることを防ぐ。

## 実体化の境界

振り返り分析と外側のハーネスの変更は別の層である。

```text
finding
   │
   ▼
proposal
   │
   ▼
explicit approval
   │
   ▼
materialization
   │
   ▼
validation / evaluation
```

初期システムは提案の生成で停止してよい。

後で実体化支援を実装する場合は、次を守る。

- 明示的なユーザー承認を必要とする。
- 対象リポジトリを基準として扱う。
- 対象リポジトリの指示と権限を適用する。
- 生成したデプロイメント出力ではなく、対象で正式な更新元となるファイルに書き込む。
- 対象の通常の仕組みで結果を検証する。

実体化によってグローバルまたはリポジトリのハーネスを黙って書き換えてはならない。

## 変更後の評価

振り返りから導いた変更は、失敗が再発し得る層で検証する。

例は次のとおり。

- Skill の振り分けの失敗 → Skill の起動または挙動の評価。
- 同じ条件で同じ結果を返す検証の不足 → チェッカーまたは CI テスト。
- 指示の失敗 → 代表的な挙動のシナリオ。
- Hook の変更 → 同じ条件で同じ結果を返す Hook の挙動のテスト。

可能な場合、非公開セッションの所見を、非公開の証拠を公開リポジトリに埋め込まず、合成回帰ケースに変換する。

## 公開・非公開の境界

この公開リポジトリに含めるものは次のとおり。

- 一般化されたアーキテクチャ。
- 一般化された振り返りの挙動。
- 合成テスト用フィクスチャ。
- 公開された実装。

次のものは含めない。

- 実際のセッション証拠。
- 非公開のハーネススナップショット。
- 非公開の所見台帳。
- 個人固有の文脈。
- 非公開リポジトリの識別子。

非公開の観測が製品に影響するのは、独立した要件または合成テストに一般化された後に限る。

## 対象外

現在のアーキテクチャは、次を提供しようとしない。

- プロバイダー固有のセッション解析。
- 継続的なセッション監視。
- プロバイダーのテレメトリー。
- 自動的なプロンプト最適化。
- 自律的なハーネス書き換え。
- エージェント品質の普遍的な評価モデル。
- エージェントの失敗に関する普遍的な分類。
- 汎用コードレビューシステム。
- 汎用リポジトリのアーキテクチャ監査。
- クラウド同期。
- Web ダッシュボード。
- 複数ユーザーの共同作業サービス。

これらの能力を追加するには、追加前に独立した証拠が必要である。
